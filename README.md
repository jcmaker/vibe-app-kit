# vibe-app-kit

김채현, 최혜지, 최재혁, 채현수가 AI 에이전트와 함께 **애플리케이션**을 만드는 레포입니다.

코드는 에이전트가 씁니다. 여러분은 **무엇을 왜 만들지 정하고, 결과를 직접 확인하는 사람**이에요. 이 README는 그 일을 잘하는 방법을 정리한 문서입니다.

---

## 1. GitHub이 뭐예요?

한 줄로 말하면 **프로젝트 폴더를 여러 사람이 함께 쓰는 공유 드라이브인데, 모든 변경 기록이 남는 곳**입니다.

구글 문서를 떠올려 보세요. 여럿이 같이 고치고, "버전 기록"에서 예전 상태로 돌아갈 수 있죠. GitHub도 비슷해요. 차이는 두 가지입니다.

- 저장할 때마다 **"무엇을 왜 바꿨는지" 메모를 꼭 남깁니다.** 그래서 나중에 "이거 언제 왜 바뀌었지?"를 찾을 수 있어요.
- 각자 **자기 작업대에서 따로 고친 다음**, 다른 사람이 확인하고 나서 본판에 합칩니다. 그래서 누가 실수해도 본판이 망가지지 않아요.

### 꼭 알아야 할 단어 7개

| 단어 | 비유 | 예시 |
|---|---|---|
| **레포 (repository)** | 프로젝트 폴더 하나 | 지금 보고 있는 `vibe-app-kit`이 레포예요. |
| **커밋 (commit)** | 메모 붙인 저장 시점 | `feat: 로그인 화면 추가` 라는 메모와 함께 지금 상태를 저장 |
| **브랜치 (branch)** | 내 작업대 (복사본) | 채현이 `chaehyun/login-page` 작업대에서 로그인 화면을 만드는 동안, 혜지는 `hyeji/home-screen`에서 첫 화면을 만들어요. 서로 방해하지 않아요. |
| **main** | 본판 | 모두가 합의한 최신 상태. 여기에 직접 고치지 않아요. |
| **PR (Pull Request)** | "제 작업대 내용을 본판에 합쳐도 될까요?" 요청서 | 채현이 PR을 올리면 재혁이 보고 "좋아요"를 누른 뒤 합쳐요. |
| **pull / push** | 받아 오기 / 올리기 | 작업 전에 pull로 최신 본판을 받고, 작업 후에 push로 내 작업대를 GitHub에 올려요. |
| **이슈 (issue)** | 할 일 메모, 버그 신고 | "저장 버튼을 눌러도 저장이 안 돼요" 같은 걸 이슈로 남겨 두면 누군가 맡아서 고쳐요. |

### 한 장면으로 보기

> 채현이 "앱에 로그인 화면을 만들고 싶다"고 생각했어요.
>
> 1. 에이전트에게 말하면, 에이전트가 최신 본판을 **pull** 받고 `chaehyun/login-page` **브랜치**를 만듭니다.
> 2. 에이전트가 코드를 쓰고, 단계마다 **커밋**합니다. (`feat: 로그인 입력칸 추가`, `feat: 로그인 버튼 연결`)
> 3. 채현이 화면을 직접 켜 보고 잘 되는 걸 확인합니다.
> 4. 에이전트가 브랜치를 **push** 하고 **PR**을 만듭니다. PR에는 "어떻게 확인하면 되는지"가 적혀 있어요.
> 5. 혜지가 PR을 보고 직접 확인한 뒤 승인하면 **main**에 합쳐집니다.
>
> git 명령어는 에이전트가 전부 칩니다. 채현은 명령어를 몰라도 돼요. 대신 **지금 어느 단계인지**는 알고 있어야 합니다.

## 2. 처음 한 번만 하는 준비

1. **GitHub 계정 만들기** — https://github.com 에서 가입하고, 아이디를 @jcmaker에게 알려 주세요.
2. **초대 수락하기** — 메일로 온 레포 초대를 수락합니다. 수락해야 이 레포에 올릴 수 있어요.
3. **AI 에이전트 설치하기** — Claude Code를 추천합니다. ([설치 안내](https://docs.claude.com/en/docs/claude-code/overview)) Cursor, Codex를 써도 됩니다. 어떤 에이전트든 이 레포의 `AGENTS.md`를 읽도록 되어 있어요.
4. **에이전트에게 세팅 맡기기** — 작업할 폴더에서 에이전트를 열고 이렇게 말하세요.
   ```
   https://github.com/jcmaker/vibe-app-kit 레포를 내 컴퓨터에 받아 줘.
   받은 다음 AGENTS.md를 읽고 세션 시작 절차대로 세팅해 줘.
   git이나 GitHub 로그인처럼 내가 직접 해야 하는 게 있으면 하나씩 알려 줘.
   ```
   GitHub 로그인(`gh auth login`)처럼 여러분이 직접 해야 하는 단계는 에이전트가 안내해 줍니다.

> Claude Code에서 이 폴더를 처음 열면 `prd-maker` 플러그인을 설치할지 물어봅니다. **설치해 주세요.** PRD를 쉽게 만들어 주는 도구예요.

## 3. 매번 작업하는 순서

```
① 시작 → ② 기획 확인 → ③ 작게 만들기 → ④ 직접 확인 → ⑤ 저장·공유 → ⑥ 인수인계
```

| 단계 | 내가 할 일 | 에이전트에게 하는 말 (예시) |
|---|---|---|
| ① 시작 | 에이전트를 열고 상황 파악 | "AGENTS.md랑 docs/HANDOFF.md 읽고 지금 어디까지 됐는지 알려 줘." |
| ② 기획 확인 | 이번에 만들 게 PRD에 있는지 확인 | "이번엔 PRD의 1단계 중 로그인 화면을 할 거야." |
| ③ 작게 만들기 | 한 번에 하나만 부탁 | "로그인 화면만 만들고, 끝나면 내가 확인할 방법을 알려 주고 멈춰." |
| ④ 직접 확인 | 내 눈으로 켜 보고 확인 | "된다고 했는데 화면이 안 떠. 무엇을 봐야 할지 알려 줘." |
| ⑤ 저장·공유 | PR을 올리고 팀에 알리기 | "커밋하고 PR 만들어 줘." |
| ⑥ 인수인계 | 다음 사람을 위해 정리 | "오늘은 여기까지. docs/HANDOFF.md 고쳐 줘." |

더 많은 예시 문장은 [docs/prompts.md](docs/prompts.md)에 있어요.

## 4. 첫 작업은 무조건 PRD

**PRD**(제품 요구사항 문서)는 "누구를 위해, 어떤 불편을, 어디까지 풀지" 적은 설계도입니다.

에이전트는 빈칸을 그럴듯한 추측으로 채웁니다. "일정 관리 앱 만들어 줘"라고만 하면 로그인을 넣을지, 데이터를 어디에 저장할지, 무엇을 뺄지 혼자 정해 버려요. 그 추측은 대개 우리가 원한 것과 다릅니다. PRD가 있으면 추측할 틈이 줄어요.

그래서 이 레포는 **`PRD.md`가 없으면 코드를 커밋할 수 없게** 막아 두었습니다. 에이전트도 PRD부터 만들자고 할 거예요.

```
/prd-maker 동아리 모임 날짜를 투표로 정하고, 정해지면 모두에게 알림이 가는 앱을 만들고 싶어
```

에이전트가 질문을 하나씩 할 거예요. 모르면 "잘 모르겠어"라고 답해도 됩니다. 그게 더 생각해 봐야 할 지점이라는 신호예요.

**PRD에서 가장 중요한 칸은 "이번에 만들지 않을 것"입니다.** 에이전트는 "말하지 않은 것"을 "빼라는 뜻"으로 알아듣지 못해요. 적어야 뺍니다.

## 5. 에이전트와 잘 일하는 법 (베스트 프랙티스)

1. **이유를 붙여서 말하세요.** "버튼 크게 해 줘"보다 "어르신들도 쓰셔야 하니까 버튼을 크게 해 줘"가 낫습니다. 이유를 알면 에이전트가 비슷한 다른 곳도 알아서 맞춰요.
2. **한 번에 하나만 부탁하세요.** 큰 일은 에이전트에게 "단계로 나눠서 먼저 보여 줘"라고 하세요.
3. **"됐어요"를 믿지 말고 직접 확인하세요.** 화면을 켜 보고, 버튼을 눌러 보세요. 확인 방법을 모르겠으면 물어보세요.
4. **"다 한 거야?"라고 물어보세요.** 에이전트는 긴 작업에서 몰래 일부를 빼먹고 "완료"라고 하는 경향이 있어요.
5. **모르는 말이 나오면 바로 물어보세요.** "그게 무슨 뜻이야? 쉬운 말로 다시."는 전혀 부끄러운 질문이 아니에요.
6. **결정은 내가, 방법은 에이전트가.** "누가 쓰는지, 무엇이 중요한지"는 여러분이 정합니다. "어떤 라이브러리를 쓸지"는 에이전트가 정하고 이유만 알려 주면 돼요.
7. **에이전트가 맞장구만 치면 의심하세요.** "내 생각에 문제 있으면 솔직하게 말해 줘"라고 해 보세요.
8. **같은 말을 세 번째 하고 있다면 규칙으로 만드세요.** "이거 AGENTS.md에 규칙으로 넣자"고 하면 다음부터는 말하지 않아도 됩니다. (규칙 추가는 PR로 팀과 함께 확인해요.)
9. **같은 오류가 세 번 나면 멈추세요.** 계속 "다시 해 봐"를 누르면 상황이 더 꼬여요. "멈추고 막힌 이유를 정리해 줘"라고 한 뒤, 팀이나 @jcmaker에게 물어보세요.
10. **끝낼 때는 인수인계를 남기세요.** 에이전트는 대화가 끝나면 전부 잊어버립니다. `docs/HANDOFF.md`가 다음 세션의 기억이에요.

## 6. 하지 말아야 할 것

- **비밀번호, API 키를 채팅이나 코드에 붙여 넣지 마세요.** 이 레포는 **공개(public)** 레포라서 올라간 건 전 세계 누구나 볼 수 있어요. 키는 `.env` 파일에만 넣습니다. (에이전트가 도와줘요.)
- **main에 직접 올리지 마세요.** 항상 브랜치 → PR → 확인 → 합치기 순서입니다. (훅이 막아 줍니다.)
- **남의 PR을 확인 없이 승인하지 마세요.** PR에 적힌 확인 방법대로 직접 해 본 뒤 승인해요.
- **에이전트가 "강제로(force)", "초기화(reset)", "지우기(delete)" 같은 말을 하면 일단 멈추세요.** 되돌리기 어려운 일일 수 있어요. @jcmaker에게 먼저 물어보세요.
- **사진·영상 원본 같은 큰 파일을 올리지 마세요.** GitHub은 코드를 두는 곳이에요.

## 7. 이 레포에 심어 둔 가드레일

여러분이 규칙을 다 외우지 않아도 되도록, 에이전트가 읽는 지침과 자동 검사를 넣어 두었어요.

| 파일 | 하는 일 |
|---|---|
| `AGENTS.md` | 모든 에이전트가 먼저 읽는 규칙. PRD 먼저 / 추측 금지·되묻기 / git·커밋 규칙 / 비밀 정보 보호 |
| `CLAUDE.md`, `GEMINI.md` | Claude Code·Gemini가 `AGENTS.md`를 읽게 연결하는 파일 (Cursor·Codex는 `AGENTS.md`를 바로 읽어요) |
| `.githooks/pre-commit` | 커밋할 때 자동 검사: main 직접 커밋 금지 / PRD 없이 코드 커밋 금지 / `.env` 커밋 금지 / 허락 안 된 문서 금지 |
| `.githooks/commit-msg` | 커밋 메모가 `종류: 무엇을 했는지` 형식인지 검사 |
| `.githooks/allowed-docs.txt` | 올릴 수 있는 문서 목록. 에이전트가 쓸데없는 문서를 마구 만들지 못하게 막아요 |
| `.github/pull_request_template.md` | PR을 올릴 때 채우는 양식 |
| `.claude/settings.json` | Claude Code에서 `prd-maker` 플러그인 설치를 안내 |
| `docs/HANDOFF.md` | 인수인계 메모. 지금 상태와 다음 할 일 |
| `docs/prompts.md` | 상황별로 에이전트에게 할 말 모음 |
| `PRD.md` | (아직 없음) 첫 작업으로 만들 설계도 |

검사에 막혔다면 에이전트에게 "왜 막혔는지 쉽게 설명하고 고쳐 줘"라고 하세요. 검사를 건너뛰는 방법(`--no-verify`)은 쓰지 않습니다.
